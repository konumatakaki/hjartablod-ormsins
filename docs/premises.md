## 主題と体験

- 中心になる問い: **「現代の道具で、接点の少ない言語を解読するとどうなるか？」**
- 扱う範囲: 言語学と言語哲学のそれなりに広い範囲
- プレイヤーが楽しむのは主に**雰囲気**。
- ゲームの回し方は**逆転裁判**に近い。矛盾を見つけて突きつけ、そこから生まれた新しい謎の中でまた矛盾を探す。
- 解読そのものは演出寄り。ただし**道具は本物**にする（例: メル周波数ケプストラム係数（MFCC）を虹色で流す可視化）。
  - 「本物」とは、本物らしく見えるように表現すること。実際に計算する必要はない（Papers, Please もパスポートのホログラムまでは作っていない）。
  - ただし、少女が実際に音声で話してくれたらとても嬉しい。
- 狙い: 「言語解読ゲーム＝言語学オリンピックのような推理パズル」というイメージを、**道具の側を強調すること**で崩す。
- 参照
  - 演出: 映画『メッセージ（Arrival）』の解析画面（Wolfram 親子が実際にコードを書いたもの）
  - UI の手触り: Papers, Please、Hacknet
- あらすじのたたき台 → `synopsis.md`

### 対応関係（オーナーが「おおむねこれに近い」と確認済み）

逆転裁判の「証言 vs 証拠」を、「**主張 vs 道具の出力**」に置き換える。
登場人物の翻訳・仮説・思い込みが証言にあたり、スペクトログラムや統計といった本物の道具の出力が証拠にあたる。
プレイヤーは頭の中で解読するのではなく、**道具を操作して、主張と食い違う出力を選んで突きつける**。
この形なら「言語学オリンピック的なパズル」から自然に離れられる。

## 役割

| 領域 | 決める人 | Claude の役割 |
|---|---|---|
| ゲームの核・世界観・キャラクター・原稿 | オーナー | 下書き、設定の整理、矛盾チェック |

オーナーは Python を最低限読み書きできる。実装は Claude が担当するが、仕組みは共有する（下の「実装の共有方針」）。

オーナーには文章執筆の経験があり、本文を直接書くこともある。
そのときの Claude の役割は、雰囲気を保ったまま誤字・脱字を拾い集めること、トーンを言葉で説明すること。

Claude のクレジットは約半月で切れる。それまでに、オーナーだけで続けられる状態を作る。
引き継ぎ資料と、データ形式の分かりやすさを優先する。

## 実装の共有方針（仮）

- 台本・辞書・設定などのデータは、コードを触らなくても編集できる形式にする。
- 事前の解析処理（音声 → MFCC など）は、なるべく読みやすい Python で書く。
- ブラウザ側のコードは仕組みを `docs/` で文章として説明する。読めなくても全体像は分かるようにする。
