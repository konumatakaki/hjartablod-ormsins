# 技術の設計（案）

必須条件（オーナー）: **ブラウザ上で、手間をかけずに遊べる。**
方針（オーナー）: Unity も候補に含め、ウェブゲームの観点から技術設計の論点を列挙して詰め直す。同じ結論になるなら、それでよい。

確度の表記がないものは確度高。

## 1. このゲームの性質

技術の選択を左右する性質:

- **文字と UI が主役。** 大量の日本語、ルビ、入れ子の注釈、窓を並べたデスクトップ風の画面。
- **動きは控えめ。** 立ち絵の差分、カメラ風のフィルター、図、簡単なミニゲーム。物理演算や 3D はない。
- **内容を書く人と、エンジンを作る人が違う。** オーナーは台本と設定を書き、Claude はエンジンを作る。半月後はオーナーだけで内容を足し続ける。
- **無料で公開する。** 収益化の仕組みは要らない。

## 2. ウェブゲームとしての論点

各論点で、ウェブ技術（HTML、CSS、TypeScript）と Unity（ウェブ書き出し）を比べる。

### 2.1 配信と起動

| | ウェブ技術 | Unity |
|---|---|---|
| 最初の読み込み | エンジン本体は数百 KB 程度。素材は必要になった分だけ読む | エンジン本体だけで数 MB〜十数 MB（構成次第。確度中）。日本語の書体を含めるとさらに増える |
| 起動までの時間 | ほぼ即時 | WebAssembly の読み込みと初期化に数秒〜十数秒（端末次第。確度中） |
| 配信の設定 | 静的ファイルを置くだけ | 圧縮形式（Brotli など）に合わせたサーバーの設定が要る。itch.io のように設定できない場所では、圧縮を解く処理をゲーム側に入れる設定（Decompression Fallback）が要る |

### 2.2 日本語の文字

| | ウェブ技術 | Unity |
|---|---|---|
| ルビ | ブラウザが標準で対応（`<ruby>`） | 標準では非対応。自作か、有料・無料の追加部品 |
| 禁則処理と改行 | ブラウザが対応（`line-break: strict` など） | TextMeshPro にある程度の設定はあるが、日本語の組版はブラウザに劣る（確度中） |
| 書体の量 | 日本語の書体を文字の範囲ごとに分割したもの（例: Fontsource の Noto Sans JP）を同梱すれば、ブラウザが使う文字の分だけ読み込む | 書体のデータを事前に作る（静的）か、実行時に作る（動的、ただし元の書体ファイルが丸ごと要る） |
| 日本語の入力（IME） | 標準で動く | ウェブ書き出しでは標準で動かない。追加部品が要る。プレイヤーに文字を入力させるなら問題になる |
| 環境による見た目の差 | OS ごとに文字の描き方が少し違う（Mac と Linux のヒンティングの差） | 自前で描くので、どの環境でも同じ見た目になる |

### 2.3 UI

| | ウェブ技術 | Unity |
|---|---|---|
| 窓、表、スクロール、注釈、ドラッグ、文字の選択とコピー | 標準の部品で作れる。見本（mock）をそのまま発展させられる | UGUI か UI Toolkit で作る。できるが、手間は多い |
| 拡大縮小 | 固定解像度の画面を CSS で縮小する。文字は縮小後の解像度で描き直されるので、くっきりしやすい | 描画の解像度を端末の画素密度に合わせて設定する |
| アクセシビリティ（文字の拡大、読み上げ） | 対応しやすい | 難しい |

### 2.4 描画と演出

| | ウェブ技術 | Unity |
|---|---|---|
| カメラ風のフィルター（粒子、色、歪み） | CSS のフィルター、SVG のフィルター、または WebGL の小さなシェーダー | シェーダーとポストエフェクトが強い |
| 図（スペクトル、MFCC） | Canvas で描く | テクスチャに描く |
| ミニゲーム（リズム、仕分け、並べ替え） | DOM か Canvas で作れる。凝るなら PixiJS などの描画ライブラリ | 強い |
| アニメーションの編集 | コードで書く | エディタで編集できる（Timeline など） |

### 2.5 音

- 両方とも、ブラウザの中では Web Audio の上で動く。制約は同じ。
- **自動再生の制限:** プレイヤーが一度クリックするまで音を鳴らせない。タイトル画面で一度クリックさせる。
- **リズムのミニゲーム:** 音の遅延は端末と環境で変わる（Bluetooth のイヤホンなど）。どちらの技術でも、遅延の補正の設定が要る。
- **本物の解析ができる:** ウェブ技術なら、再生中の音声から Web Audio の解析機能（AnalyserNode）でスペクトルをその場で計算して描ける。「道具は本物」を、少女の声の実際の音声データで実現できる。Unity にも同様の機能はある。

### 2.6 セーブ

- ブラウザの保存領域（localStorage、IndexedDB）に保存する。Unity の PlayerPrefs も、ウェブでは IndexedDB に保存される。
- **Safari は、7日間そのサイトを使わないと、スクリプトが保存したデータを消すことがある（ITP）。** → セーブデータをファイルに書き出す機能と、読み込む機能を付ける。
- **itch.io では、複数のゲームが同じドメインから配信されるため、保存領域の名前がほかのゲームと衝突しうる（確度中）。** → 保存の名前に、このゲーム固有の接頭辞を付ける。

### 2.7 画面と端末

- **全画面:** iPhone の Safari は、動画以外の要素の全画面表示に対応していない。iPad は対応。
- **スマホ:** Unity は Unity 6 からスマホのブラウザを正式に支援するようになった（確度中）が、メモリの制限で落ちやすい。ウェブ技術は軽いが、窓を並べた画面は小さい画面と相性が悪い。どちらでも「PC が主」になる。
- **itch.io の埋め込み:** ゲームは iframe の中で動く。キーボードの入力は、ゲームの画面を一度クリックするまで届かないことがある。

### 2.8 開発と保守

| | ウェブ技術 | Unity |
|---|---|---|
| 必要な環境 | ブラウザと Node.js（エンジンの変更時のみ）。内容の確認は `python -m http.server` で足りる | Unity エディタ（数 GB）とライセンスの有効化 |
| オーナーが内容を書き足す | テキストファイルを書き換えて再読み込み。ビルド不要 | 内容を外部ファイルにすれば同様にできるが、エンジンを含む変更にはエディタでのビルド（数分）が要る |
| **Claude が作業環境で作り、試せるか** | **できる。** ビルド、起動、Playwright での自動スクリーンショットまで、この作業環境で完結する | **ほぼできない。** この作業環境で Unity エディタを動かしてビルドするには、ライセンスの有効化が必要で現実的でない。Claude はコードを書けても、動かして確かめられない。確認と修正の往復がオーナー側に移る |
| バージョン管理 | テキストなので差分が読みやすい | シーンやプレハブの差分が読みにくく、衝突の解消が難しい |
| ライセンス | ink、inkjs、Preact、Vite はすべて MIT。書体は OFL など | Unity Personal は無料（売上が一定以下）。2024年に、インストール数に応じた料金の導入は撤回された |

### 2.9 将来の展開

- PC 向けの配布（Steam など）をしたくなったら: ウェブ技術は Electron や Tauri で包めば出せる。Unity はそのまま出せる。
- ここは Unity の明確な利点。ただし、今回の必須条件ではない。

|---|---|---|---|

| 日本語の文字、ルビ、注釈 | 最重要 | ◎ | △ |
| 窓を並べた UI | 重要 | ◎ | ○ |

## 4. 構成（詰め直し後）

| 部分 | 使うもの | 理由 |
|---|---|---|
| 画面と操作 | TypeScript、Preact | 窓の UI は DOM が最も得意。Preact は小さく、React と同じ書き方なので後から触る人にも分かりやすい |
| 演出とミニゲームの層 | Canvas。必要なら WebGL の小さなシェーダー（凝るなら PixiJS） | カメラ風のフィルター、図、リズムのミニゲームは、DOM の上に重ねた Canvas で描く |
| 台本の進行 | ink と inkjs | 分岐、変数、選択肢、状態の保存が揃っている。専用エディタ Inky で台本だけを試し読みできる。言語解読ゲーム『Heaven's Vault』はこの ink で書かれている |
| 演出の指示 | ink のタグ（例: `# cam: 正面 / 目線: 下`） | 台本の中に立ち絵や道具の指示を書ける |
| 音 | Web Audio（AnalyserNode でスペクトルを実際に計算） | 少女の声の実際の音声から図を描ける |
| 書体 | 同梱。日本語は文字の範囲ごとに分割された Noto Sans JP | 必要な分だけ読み込む。内容を書き足しても、ビルドし直さずに新しい文字が表示できる |
| セーブ | localStorage（固有の接頭辞）＋ファイルへの書き出しと読み込み | Safari の自動削除と、itch.io での衝突への対策 |
| ビルド | Vite | 最終的にはただの静的ファイル |
| 公開 | itch.io と GitHub Pages | どちらも無料。リポジトリはすでに公開されている |
| 確認 | Playwright | 自動でスクリーンショットを撮り、design-rules.md のチェックに使う |
| 内容の検査 | Python のスクリプト | 用語集の参照切れ、ルビの書式の誤りなど。オーナーが読める言語にする |

### 内容とエンジンを分ける

- **エンジン**（TypeScript）: Claude が作る。変更にはビルドが要る。
- **内容**（台本、用語集、語彙、表記の層のデータ、画像、音声）: テキストファイルと素材のフォルダ。起動時に読み込む。
  → オーナーは内容のファイルを書き換えて、ブラウザを再読み込みするだけで確認できる。

### 台本の書き方のイメージ（ink）

```ink
=== day1_first_contact ===
# cam: 正面 / 表情: 真顔
私は|椅子《いす》に座り直した。インフォーマントの前では、まず姿勢から。
* [見せる: 絵カード「パンを食べる人」]
    # show_card: bread
    # utter: g_001
    少女は絵を見て、両手を胸の前で合わせた。
    -> bread_reaction
* [待つ]
    -> wait
```

ルビ `|漢字《よみ》` と用語の印は、ink の文字列の中にそのまま書き、表示のときにエンジンが変換する。

## 5. オーナーの判断（確定）

- **ロード時間はそこまで重要ではない。** 1時間ほど遊ぶゲームなので。
  → 評価表の「起動の速さ」の重みは下がる。それでも、日本語の文字、UI、Claude が作って試せるかの3点でウェブ技術が有利なので、結論は変わらない。
- **文字の入力は、させないか、させても単純なものだけ。** 操作は選択肢とドラッグが中心。日本語の入力（IME）は設計から外す。
- **セーブデータが消えるのは、そういうものとする。** ファイルへの書き出しは必須ではない（余力があれば付ける）。
- **スマホでの遊びは想定しない。** ただし、タップだけで操作できるようにする。
  → カーソルを合わせる操作（ホバー）やキーボードを必須にしない。注釈はクリック（タップ）で開く。ドラッグは Pointer Events でマウスとタッチをまとめて扱う。

## 6. 解像度（Claude の推し: 論理解像度 1280×720）

DOM で作る場合、「固定解像度」は**レイアウトの座標系**であって、描画の画素数ではない。文字は、縮小・拡大した後の実際の画素数で描き直される。
なので、決めることは2つに分かれる。

### 6.1 レイアウトの座標系: 1280×720

- **ブラウザの中の画面は、モニターより小さい。** ブラウザの枠や itch.io の埋め込みの分だけ狭く、実際の表示幅は 1000〜1900px 程度になる。
- 1920×1080 で組むと、ほとんどの環境で縮小表示になる。dwm のバー（約15px）や端末（12px）の、本物どおりの小さな文字が 8〜10px 相当まで縮んで読めなくなる。
- 1280×720 で組めば、多くの環境で等倍〜1.5倍の表示になり、本物どおりの文字の大きさのまま読める。
- 仮想マシンの画面としても、1280×720 前後は自然（仮想マシンの画面は、初期設定では小さめの解像度で起動することが多い。確度中）。

### 6.2 素材の解像度: 座標系の2倍で作る

- 拡大表示（最大1.5倍程度）と、高精細な画面（Retina など、画素密度2倍）が重なると、論理の1px が実際の3px 前後になる。
- 素材は**座標系の2倍**で作れば、ほとんどの環境で十分。
  - 例: カメラの窓（704×700）に出す立ち絵は、1408×1400 程度で用意する。
  - NovelAI の通常サイズ（1216×832 など）で生成し、拡大機能を使えば届く。カメラ風のフィルターが、拡大の粗を目立ちにくくする。
- 図（スペクトル、MFCC）やフィルターの Canvas は、実際の画素数（論理サイズ × 表示倍率 × 画素密度）で描く。そうしないとぼやける。

### 6.3 確認の仕方

- Playwright で、幅 1000px、1280px、1920px、画素密度1倍と2倍の組み合わせでスクリーンショットを撮り、文字と素材のくっきり具合を確かめる。

### 6.4 決定

- 論理解像度は 1280×720。素材は2倍で作る（確定）。
- カメラの映像は、16:9 の全体から顔の周りをトリミングして、カメラの窓に出してよい（確定）。

## 7. 未決

- 逆転裁判のような失敗のペナルティ（体力ゲージなど）を持つか。状態の設計に関わる。
